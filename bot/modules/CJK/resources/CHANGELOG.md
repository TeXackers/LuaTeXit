# Changelog

Here I document the notable changes to `unihan_cache.json` (generated by `build_cache.py`, not here though).


## v14
Add Unicode's `EquivalentUnifiedIdeograph.txt` into `kSpoofingVariant` per [UAX #38](https://www.unicode.org/reports/tr38/index.html#Spoofing).
- 125 characters  with 140 new links as a result.

## v13
New `designations` section per character, recording the lists and levels it's designated under for Korea, Japan and Hong Kong.
- `korean_education` (1800): there's 900/900 split across 中學校/高等學校, processed in `korean_education_level.json`.
- `korean_name` (6367) from `kKoreanName` for names
- `hanja_exam` (5978) from `hanja_exam_level.json`, 8級 through 特級.
- `joyo` (2136) from `kanji_level.json`, which splits the Jōyō kanji into school grades. Grades 1-6 (1026) and 中学年 (1110).
- `jinmeiyo` (647) from its 人名用 list.
- `hong_kong_grade`, i.e. 香港小學學習字詞表 (香港小學學習字詞表) (1-6年級) from `kGradeLevel` in Unihan.

## v12
Two new variant sources, both mined from additional Unihan files - discovered from `篆`/`蒃` and `姬`/`姫` having no link in any `kXXXVariant` field.
- Mine `kCCCIIVariant` from `kCCCII`/`kEACC` in `Unihan_OtherMappings.txt`.
- 544 links pointing at a Japan-only glyph are re-filed under `kJapaneseNewVariant` as well, e.g. `鬱`:`欝`, `姬`:`姫`, `歲`:`歳` etc., derived from `kUnihanCore2020`.
  - Neither pair is in the shinjitai table, both being 拡張新字体 rather than official forms.
  - The reverse link is only typed `kTraditionalVariant` when that side isn't itself a simplification, since e.g., `発` links to both `發` and `发`.

N.B. I found characters like `㭗` (unlinked) that have no CCCII code and no Unihan variant field but then their identification differs by tradition (`鬱` in Korea, `皿` in Cantonese).

## v11
Readings are now ranked, such that `pronunciations[category][0]` is the usual reading cf. whichever was sorted first.
- Discovered from `勉子孫行善詩` reading as `miễn tí tôn hàng thiến thi`; and `行` in Korean reading using `항` over `행`.
- For Korean, `table.json` was used as preferential readings which fixes about 440 characters.
- `vietnamese` is ordered by KanjiDictVN gloss count per reading, ties broken by a Cantonese pivot `rank_vietnamese`.

N.B. Reading sets themsselves remain unchanged. Ranking runs before `apply_variant_fallback` so borrowed readings inherit it.

## v10
- Rename the v9 variant fields from `kShinjitaiVariant` to `kJapaneseNewVariant` (which seems to be in Unicode 18 Beta). I changed `kKyujitaiVariant` to `kTraditionalVariant` for now (but could be `kJapaneseOldVariant` which is also in Unicode 18 Beta)
- Update `VARIANT_FALLBACK_FIELDS` to match. `kJapaneseNewVariant` keeps first priority, `kTraditionalVariant` stays in its original (last) position since it's now a merged field.

## v9
- Move resources under `resources/`.
- Integrate the [Shinjitai/Kyujitai table](https://github.com/dahlia/shinjitai-table) as new variant links (`kShinjitaiVariant`/`kKyujitaiVariant`)
  - Discovered from 發 and 発 not linking.
- However, pairs involving a CJK Compatibility Ideograph (U+FAxx) are skipped, since Unihan itself excludes those and has no entry for them (might change)
- Add these fields to `VARIANT_FALLBACK_FIELDS` with top priority,
- Fix `apply_variant_fallback` so that multi-hop chains now resolve deterministically.
  - Discovered from 鬥, 鬭, 闘.

## v8
- Integrate `table.json` from [hanja](https://github.com/suminb/hanja) (which has 27K entries) as an additional `korean_hangul` source, unioned with Unihan's `kHangul` field.
- Where a character's only prior `korean_hangul` value came from variant fallback (v7) rather than direct Unihan data, `table.json`'s direct reading now supersedes the inferred one.

## v7
- Generalise the variant-fallback mechanism from v6 to run against all pronunciation categories, not just Vietnamese i.e. fixes cases like 為 (no `kHangul` of its own) now correctly inheriting `korean_hangul: ["위"]` from its `kSemanticVariant` 爲.
- Fallback runs as a final pass over a pre-fallback snapshot, so borrowed readings never chain transitively through another character that itself just borrowed.

## v6
- Add variant-fallback for the KanjiDictVN Vietnamese lookup
  - identified from 絕 having no pronunciation.
  - when a character has no direct KanjiDictVN entry, its `kZVariant` / `kSemanticVariant` / `kSimplifiedVariant` / `kTraditionalVariant` are checked for one.

## v5
- `vietnamese` pronunciations unioned with [KanjiDictVN](https://github.com/trungnt2910/KanjiDictVN) (about 10K Hán Việt readings).

## v4
- Add `pronunciations` section per character, consolidating and deduplicating readings across `cantonese`, `mandarin`, `japanese_on`, `japanese_kun`, `korean_hangul`, `korean_romanized`, and `vietnamese`, merged from all relevant raw Unihan fields (e.g. `mandarin` unions `kMandarin`, `kHanyuPinlu`, the Mandarin half of `kSMSZD2003Readings`, and the pinyin halves of `kHanyuPinyin`/`kXHC1983`/`kTGHZ2013`).
- Remove the raw fields consumed by `pronunciations` (`kCantonese`, `kHangul`, `kHanyuPinlu`, `kHanyuPinyin`, `kJapanese`, `kJapaneseKun`, `kJapaneseOn`, `kKorean`, `kMandarin`, `kSMSZD2003Readings`, `kTGHZ2013`, `kVietnamese`, `kXHC1983`) no longer appear separately under `readings`. Only `kDefinition`, `kFanqie`, `kTang`, `kZhuang` remain there.

## v3
- Change behaviour of multi-value reading fields (e.g. `kJapanese`, `kCantonese`) which are now JSON lists instead of single space-joined strings, for predictable typing. `kDefinition` remains as a single string.

## v2
- Fix `kHangul` values (e.g. `"구:0E"`): stripped down to just the Korean reading (`"구"`).
- Fix `kHanyuPinlu` values (e.g. `"qiū(58)"`): stripped down to just the pinyin (`"qiū"`).

## v1
- Initial build: parse `Unihan_Readings.txt` and `Unihan_Variants.txt` into a single dict keyed by character with `readings` and `variants` sections, written to `unihan_cache.json`.
